# 场景：客户现场「输入有 PWM、输出无波形」工单闭环

**性质说明**：工单文本为合成的脱敏样本；现场日志直接取自 `examples/pwm_issue/input/serial_before.log`
（同一失败模式同结构脱敏样本）。本场景演示的是**流程**：从客户工单到根因假设、建议动作与回复稿，
每一步都留下可追溯的证据，而不是"让模型写一段话"。

## 场景

客户（整机厂）反馈：驱动板上电后示波器测相 A 无输出，MCU 侧 PWM 波形正常。
现场工程师已抓一段串口日志、说明供电与负载条件，发来工单。

## 这条场景链路上每一步的产物

| 步骤 | 用什么 | 产物 |
|---|---|---|
| 1 解析工单 | 工单文本 + 关键字段抽取 | 现象 / 器件 / 环境 / 期望 |
| 2 检索历史故障 | `kb_search`（RAG：词法 + 向量 + RRF） | 命中 `examples/pwm_issue`，带 `path#L行` 引用 |
| 3 日志断言 | `log_check` + `evals/log_rules/pwm_before.yaml` | 断言通过/失败明细 |
| 4 根因假设与动作 | 上一步证据 + 历史案例 | 排序后的假设与验证动作 |
| 5 客户回复稿 | 上述全部 | `traces/field-<id>/report.md`（含引用，可直接改成人话发出去） |

## 为什么它算"业务场景纵深"

仓库前面的例子是**工程视角**（改代码、跑评测），这个场景是**业务视角**：
输入是一张客户工单，输出是一份给客户的回复与一份内部根因报告；
中间的检索、断言、引用全部复用已有工具，没有为演示新写一套旁路逻辑。
